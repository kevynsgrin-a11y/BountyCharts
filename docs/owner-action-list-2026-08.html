1 · Deployment topology — do these two first

Check branch protection on mainBlocking

This single setting decides whether audit finding C3 is critical or merely untidy. With it, a red validate check stops a merge and the gate still holds at the merge boundary. Without it, the gate is advisory only.

Repo → Settings → Branches → add a rule for main → tick Require status checks to pass before merging → select validate.

Decide which deploy path is authoritativeBlocking

Measured: the GitHub Actions deploy job runs with its Cloudflare step skipped (no secrets), while Cloudflare Pages' own Git integration deploys the site independently. Across three consecutive pushes the Pages build began 4 s, 2 s and 4 s before the validate job even started — so the deploy is not conditioned on the gate at all. Two paths exist; the one with the gate in front of it is the one not running.

Option A — keep Pages Git integration (recommended, it is what already works):

  • Do the branch-protection step above; that becomes the real gate.
  • Delete the deploy job from .github/workflows/deploy.yml.
  • Rewrite docs/deployment/cloudflare.md steps 3–4, which currently describe a secrets-based path that is not the live one.

Option B — use the workflow instead: disconnect Git integration in the Pages project, then add both repo secrets:

Repo → Settings → Secrets and variables → Actions → New repository secret
  CLOUDFLARE_API_TOKEN     (Account → Cloudflare Pages → Edit)
  CLOUDFLARE_ACCOUNT_ID    820e7cee61fccc60d14c8e20bc686942

Do not do both. With Git integration active and the secrets added, both paths deploy the same project on every push and race each other.

2 · Domain and live verification

Attach the custom domain and canonicalise wwwDecision

The site currently serves only on *.pages.dev. Every canonical URL, the og:image URL and the sitemap already point at https://bountycharts.com/, so those are promises the DNS does not yet keep.

Pages project → Custom domains → add bountycharts.com and www.bountycharts.com. Then zone → Rules → Redirect Rules:

When:       Hostname equals www.bountycharts.com
Then:       Dynamic redirect, 301, preserve query string
Expression: concat("https://bountycharts.com", http.request.uri.path)

Run five checks I could not — the live URL is egress-blocked hereVerify

Audit finding L5 is the only one still graded INFERRED, purely because of this. Paste and eyeball:

curl -sSI https://bountycharts.com/            | head -1     # expect HTTP/2 200
curl -sSI https://bountycharts.com/            | grep -i cache-control
curl -sSI https://bountycharts.com/nope        | head -1     # expect HTTP/2 404
curl -sSI https://www.bountycharts.com/        | head -3     # expect 301 to apex
curl -sSI https://bountycharts.com/            | grep -i set-cookie   # expect nothing

The one to look at closely is line 2. _headers sets Cache-Control: max-age=0, must-revalidate on /*.html, but the landing page is served at /, which may not match that pattern — leaving the most cache-sensitive page on Cloudflare's default policy. If no must-revalidate comes back, add an explicit rule for / in site/_headers.

Line 5 settles the last open question: whether the edge sets cookies. If anything comes back, a privacy claim of "no cookies" cannot be made.

Cross-browser and unfurl spot-checksVerify

Everything measured in this audit was Chromium-only. Three things are worth a 30-second look each in Safari and Firefox:

  • CSP. script-src no longer allows 'unsafe-inline'. Zero violations in Chromium; confirm the console is clean elsewhere.
  • Favicon. It is an inline SVG data URI. Confirm the tab icon shows a gold diamond, not a blank page.
  • Print. With your OS in dark mode, print-preview the page. It must come out white with black text and the GitHub URL printed after the link.

Then paste the live URL into Slack, iMessage and X and confirm the social card renders wide, not as a small square.

Answer four questions, then the disclosures page can be writtenDecision

A /disclosures page was specified and deliberately not built. Naming the company is not enough — the page has to make claims about conduct, and inventing those on a site whose entire pitch is verifiability would be worse than having no page. Your answers:

  1. Positions. Do you or the LLC hold, trade, or speculate in any card or sealed product the site will cover? (A clean "no positions" statement is the single most valuable line on such a page — but only if true.)
  2. Affiliates. Any existing relationship with TCGplayer or another retailer, signed or pending?
  3. Analytics. Will anything be measured at launch? Cloudflare Web Analytics is cookieless and needs no consent banner; anything else changes the privacy copy.
  4. Cookies. Settled by the curl in §2 above.

Timing matters on #2. docs/deployment/cloudflare.md records that an affiliate disclosure is legally required before the first affiliate link ships, not after. If a link is imminent, this page becomes blocking.

Confirm the darker brand goldVerify

Shipped, because it was an accessibility defect rather than a taste question — but it is your brand, it is visible, and it is one commit to revert.

TokenWasNowContrastUsed for

All are hue-preserving darkenings, not new hues. Hover now darkens rather than lightens, which is why --gold-bright moved so far. Two standing rules: never apply opacity to these three light-theme tokens — they clear the 4.5 threshold by about 0.01 and all three re-break at once — and recompute if --bg ever changes.
